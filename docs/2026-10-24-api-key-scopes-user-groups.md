# 用户组集中管理与 API Key 独立权限

## 界面变化

- 公共按钮高度调整为默认 36px、小号和表格操作 32px、大号 44px；默认字号 14px，表格和小号 13px，图标 16px。继续统一圆角、间距及深浅主题颜色。
- 基础管理 → 授权管理的第三个页签改为「用户组」，包含「资产用户组」和「容器用户组」。两类用户组仍使用各自的数据、成员及授权 API，不迁移或混合已有成员关系。
- 容器授权保留用户权限、RBAC 角色、RBAC 绑定和我的权限。容器用户组管理移动到「用户组 → 容器用户组」。
- 移除独立「角色权限」页面及角色列表的跳转按钮。旧 `/system/role-permission` 地址重定向到 API Key；用户登录角色、菜单权限与历史授权数据保留。
- 「API Token 管理」统一命名为「API Key」，用户列表和页面操作改为「分配 Key」。

## 分配 Key

管理员进入 **基础管理 → API Key → 分配 Key**，填写名称、所属用户、有效期，并明确勾选权限范围。权限矩阵沿用原角色权限的模块及操作目录，支持搜索模块、全部设为只读、清空授权和已选计数。至少选择一项；接口同时校验空值、重复、未知权限与继承标记，不接受 `*`。

每个新 Key 独立配置模块权限，**不与所属用户的角色模块权限取交集**，也不会给用户的浏览器登录添加权限。未勾选的操作始终拒绝，管理员所属的 Key 同样受此限制。只选择写入或执行不会隐式授予读取，集成通常还需要该模块的 `read` 权限。

资源范围继续使用所属用户的资产、集群、命名空间和 Kubernetes RBAC 授权；管理员专属接口仍要求所属用户是活动管理员。API Key 不可修改个人登录资料或密码；新 Key 的分配、撤销与历史角色模块授权管理使用管理员登录会话，防止 Key 再生成更宽范围的 Key。

Key 明文仅生成时显示一次，列表展示前缀与权限摘要，可展开所有权限。数据库只保存随机 Token 的 SHA-256 摘要。调用格式保持 `Authorization: Bearer <API_KEY>`。

账号停用、Key 过期或撤销会使后续请求失效；撤回资源授权立即影响后续资源访问。Harness 回调按票据中的 Key ID 重新读取 Key 与资源权限，不能借所属用户的管理员身份或角色权限跳过 Key 范围。已经执行的操作不会回滚，现有长连接的关闭行为未在本次扩展。

## 接口和升级

- `POST /api/v1/system/api-keys`：`{"userId":2,"name":"Docker 集成","days":30,"scopes":["docker:read","docker:execute"]}`。返回 `{key, token}`，仅该响应包含明文。
- `GET /api/v1/system/api-keys/catalog`：管理员读取 `{modules}`，复用统一权限目录。
- Key 列表返回 `grantMode`、`scopes` 与 `modules`；`grantMode="scoped"` 表示新独立模式。列表仍按所属用户隔离，管理员可以筛选用户。
- `GET /api/v1/system/permissions/me` 对新 Key 返回该 Key 的有效模块范围，不返回所属管理员的全量权限绕过标记。
- 启动时 AutoMigrate 新增 `sys_api_key.grant_mode`（默认空字符串）并将 `scopes` 扩为 TEXT，避免多模块权限超过原 200 字符限制。`api/sql/autoops.sql` 同步初始化结构。
- 旧 Key 的模式保持空字符串：`user:inherit` 继续继承用户角色权限；旧 `aiops:*` Key 继续受原接口白名单约束，不自动扩权。需要独立范围时撤销旧 Key 后重新分配。
- 导航迁移合并旧角色权限入口与 API Key 菜单，保留菜单关联并防止重复创建。不需要新增 Docker 或 Kubernetes 配置。

升级时同时发布前后端并重启 API，以应用字段和菜单迁移；本次没有连接业务数据库或部署运行服务。
