# Web 集群 Keepalived / VIP

Web 集群可以选择 2–10 台不同主机上的已接管 Nginx 实例，用 Keepalived 维护一个 IPv4 VIP。Docker 实例仍支持数据源、配置和日志，当前 VIP 执行器仅用于 Linux 主机实例。

## 从页面接入高可用

入口是 **Web 管理 → 集群管理 → 详情 → 高可用 / VIP**，详情页的“高可用配置教程”可随时打开。不要把“首选节点”理解成当前实际持有者，实际持有者以拓扑中的采集结果为准。

1. 在数据源管理中登记宿主机和 SSH 档案，执行识别及发现。选择实际受管的 Nginx，核对主配置、PID、监听端口及健康 URL；同机存在系统 Nginx 时不能选错实例。
2. 新建集群并通过成员管理加入实例。业务分组一致，完成接管，保证每个节点的业务配置和健康地址可用。环境可从生产、预发布、测试、开发及已有值中选择，也可清空或新增自定义值。
3. 在各主机确认网卡名称、子网和物理地址一致对应；为 VIP 预留地址，节点间放通 VRRP（IP 协议 112），允许所需业务端口。VIP 不应另配为某台机器的永久静态地址。
4. 打开高可用面板填写下表，点击“配置 VIP”。预检显示目标、依赖、冲突与权限结果；有失败项时先修复原因，再重新预检。
5. 确认计划后等待任务成功，查看唯一持有者，并从客户端访问 VIP 的健康或业务地址。可用“核验 VIP”执行即时核验；拓扑本身读取后台快照。

| 字段 | 本次三节点示例 | 如何选择 |
| --- | --- | --- |
| VIP/CIDR | `192.168.80.110/24` | 已预留、同子网、未被占用的 IPv4 地址与掩码 |
| 网卡 | `ens33` | 三个节点实际承载该网段的同名网卡，不填容器网桥 |
| VRID | `151` | 1–255，不能与同网段其他 Web/数据库 VRRP 组冲突 |
| 成员 | 实例 1、2、3（`.51/.52/.53`） | 2–10 台不同主机上的已接管主机实例 |
| 首选节点 | 实例 1 | 首次部署优先顺序；不保证后续故障恢复后自动抢回 |
| 实例健康 URL | `http://127.0.0.1:18080/__autoops_health` | 每台本机可访问，实际服务还需监听通配地址或 VIP |

### 切换持有者与更换地址

**换主节点**：详情 → 高可用 / VIP → 核验 VIP → 预检并确认；全部备份健康后，再“切换 VIP” → 预检 → 确认。地址仍是 `.110`，健康备份由 VRRP 选举接管。完成后检查任务、拓扑及业务响应；当前不提供指定目标强制接管。

**换 VIP 地址**：当前版本尚未实现已部署地址的迁移、退役及成员扩缩容，相关字段会锁定，“切换 VIP”不是改址。不要直接改数据库、删元数据或手工追加地址。正式改址需要独立迁移能力，至少涵盖新地址冲突检查、全部节点配置替换、新入口探测、DNS/客户端入口更新、失败恢复旧地址；在该流程实现前，平台内没有可执行的改址步骤。本次没有更换或重新绑定现有 `.110`。

## 配置与执行

在集群详情查看拓扑，从“配置 VIP”填写 VIP/CIDR、网卡、VRID 和实例；优先实例可选。要求管理员身份、Web 执行动作与目标资产授权，以及对应主机的命令执行权限；API Key 同样受模块和资产范围限制。集群与成员必须已接管，SSH 档案必须启用且可写。主机网卡名必须一致，业务健康检查协议、端口及路径也必须一致。

优先实例先部署，其余实例按选择顺序排列，优先级依次为 `200、190、180……`。未选择优先实例时，以成员列表第一项为首选。使用 `BACKUP`、`nopreempt` 和单播 peer 列表，切换后原节点恢复为备份，避免立即抢占回切。“切换 VIP”让当前持有者让出 VIP，由健康备份按 VRRP 选举接管；当前不提供指定目标节点强制接管功能。

所有动作均走操作计划、确认、持久化 Worker 和集群锁：

- `configure-vip`：冻结成员、源版本、Nginx 身份/配置摘要、物理地址、对端 MAC、VIP 配置和缺失依赖包版本；执行时重新预检，每加入一个节点都先核验唯一绑定和业务 HTTP，再继续。
- `verify-vip`：核验独立服务、各 Nginx 本机健康、唯一持有者，以及从节点经 VIP 访问业务健康地址。
- `switch-vip`：核验全部备份，给当前持有者设置独立的 120 秒 systemd 救援定时器，然后只停止该节点的 Web VIP 单元；新节点接管并通过业务探测后启动原单元并取消定时器。Nginx 不会因此重启。
- `reconcile`：原任务结果不明时，按原任务的远端证据核验或恢复，具体规则见下文。不会重放原部署或切换命令，外部漂移会保留原锁并提示冲突。

普通集群编辑不能修改已部署 VIP；VIP 成员也不能直接移出集群，避免远端高可用服务失去管理归属。已部署集群再次提交相同 VIP 配置只执行核验，改变地址、VRID、网卡或成员会被拒绝。当前未提供 VIP 退役、改址和成员扩缩容入口，不应通过删除元数据或远端文件绕过这些约束。

## API 与本次绑定参数

`GET /api/v1/web/clusters/:id/topology` 返回实例、入口和 VIP 观测结果。创建计划使用 `POST /api/v1/web/operation-plans`；以下为本次集群 `1` 已部署的参数示例，实例 ID 对应 `.51、.52、.53`，不是 CMDB 主机 ID：

```json
{
  "targetType": "clusters",
  "targetId": 1,
  "action": "configure-vip",
  "parameters": {
    "vip": {
      "cidr": "192.168.80.110/24",
      "interface": "ens33",
      "routerId": 151,
      "instanceIds": [1, 2, 3],
      "preferredInstanceId": 1
    }
  }
}
```

VIP 仅接受可用 IPv4 主机地址，掩码前缀范围为 `8–30`，VRID 为 `1–255`，成员为 `2–10` 个不同主机上的实例。本次三台实例的本机健康 URL 均为 `http://127.0.0.1:18080/__autoops_health`，对应 VIP 探测为 `http://192.168.80.110:18080/__autoops_health`；18080 端口由各目标 Nginx 监听在通配地址。18082 反向代理和 18443 TLS 的额外验收结果记录在验收文档中。

计划所有检查通过后，通过 `POST /api/v1/web/operations` 提交 `{ "planId": <返回的计划ID>, "idempotencyKey": "<本次提交的唯一键>", "confirmed": true }`，随后查询 `GET /api/v1/web/operations/:id`。重试同一提交保留原幂等键。核验和切换计划分别将 `action` 改为 `verify-vip`、`switch-vip`，`parameters` 使用 `{}`，由后端读取已冻结的集群 VIP 配置。核验中断任务使用 `action: "reconcile"`，并传入 `parameters: { "operationId": <原任务ID> }`。

## 预检与部署边界

预检检查主机执行授权、可写 SSH 档案、同网段物理地址、CMDB 地址冲突、已登记的数据库/Web VIP 与 VRID、远端已有配置、ARP 应答和 VRRP 广告。已有数据库 VIP 的 secondary 地址不会被误当成主机物理地址。Nginx 健康 URL 必须指向本机，端口必须由当前实例的实际 master 监听在通配地址或 VIP；仅监听 localhost 的业务端口不能接入 VIP。

每集群独立使用：

- 配置：`/etc/autoops-web-vip/<clusterId>/keepalived.conf`
- 实例健康脚本：`/etc/autoops-web-vip/<clusterId>/health.py`
- systemd 单元：`autoops-web-vip-<clusterId>.service`
- systemd 单元文件：`/etc/systemd/system/autoops-web-vip-<clusterId>.service`
- PID：`/run/autoops-web-vip-<clusterId>.pid` 和 `/run/autoops-web-vip-<clusterId>-vrrp.pid`
- 执行记录：`/var/tmp/autoops-web-vip/<clusterId>/<operationId>.json`

不会覆盖或重启系统 `keepalived.service`、数据库 `autoops-db-vip-*` 单元或 Nginx 单元。健康脚本校验本实例 PID 文件、二进制、配置入口、`nginx -t` 和 HTTP 响应，不能用“机器上存在 nginx 进程”代替实例健康。

Debian/Ubuntu 缺少 Keepalived 时，预检要求 APT 包索引中存在可用版本；必要时先更新包索引。解析 `apt-cache policy` 固定 `LC_ALL=C`，兼容中文主机。Worker 按预检冻结的版本安装，并临时屏蔽默认系统单元启动；已经安装 Keepalived 的主机不升级该包。失败回退保留已安装依赖包，只恢复本次新建的独立 VIP 配置和服务。

## 状态与恢复

拓扑读取后台约每 30 秒采集的快照，显示实际持有者、服务状态、节点健康和原始采集时间；GET 接口不再串行连接三个 SSH 节点。快照超过 90 秒、配置摘要不匹配或采集时间异常时显示未知并清除旧持有者，点击刷新不伪造新的采集时间。“核验 VIP”任务仍执行即时远端检查。只有所有成员的独立 VIP 服务及本机 Nginx 健康、恰好一个节点绑定 VIP、各节点经 VIP 的业务探测通过，才显示 `healthy`。多个持有者为 `conflict`，无持有者为 `unavailable`，服务或业务探测失败为 `degraded`，无法确认远端状态为 `unknown`。列表采集器也核验 VIP，故障会反映到集群状态。运行中或待核验任务仍保留互斥锁；Nginx 配置发布、证书部署与 VIP 操作共用集群边界，证书签发本身不等同于部署。

任务网络中断或执行结果不明时不要重提部署或手动删除锁，先执行“核验中断任务”。文件被人工修改、源连接发生变化、journal 不完整且无法证明回退范围时，核验拒绝覆盖。新部署检测到明确多持有者冲突，会停止后续节点并按原清单回退新建 Web VIP；已有数据库 VIP 不参与回退。

恢复任务先检查当前恢复操作者的权限、原始数据源版本和 Nginx 身份/配置基线，再检查以下证据：

- 新建 VIP 部署：核验本次变更节点的原任务 journal、文件清单和摘要。尚未开始的节点必须没有对应 VIP 服务；部分完成的部署只按原清单移除本次创建的单元、配置与健康脚本。证据完整且全部完成时，再核验实际持有者和业务。
- VIP 切换：原持有者需要原切换任务 journal；其他未变更节点核对原计划冻结的 VIP 文件摘要，不要求它们具有切换 journal。恢复时可重新启动原持有者的独立 VIP 服务并取消救援定时器，然后核验。若最终仍由原节点持有 VIP，原切换任务记为 `rolled-back`；由其他节点持有且全部核验通过则记为 `succeeded`。
- 只读核验及已有相同配置的核验：比较原计划冻结的 VIP 文件摘要和当前状态，不创建或要求远端变更 journal。

恢复任务使用原操作 ID 查找远端证据，授权检查使用当前恢复操作者。核验失败保留原任务和集群/VIP 互斥锁；只有确认成功或确认回退完成才释放原锁。新部署回退后，原任务记为 `rolled-back`，恢复任务记为 `succeeded`，依赖包保留。

VRRP 需要节点间 IP 协议 112 可达，Keepalived 本身不提供多数派隔离。在网络分区下仍可能出现多个持有者，因此不能把一次切换验证等同于任意网络故障下无中断；拓扑会明确显示 conflict。

协议和参数依据：[Keepalived 配置文档](https://www.keepalived.org/documentation/keepalived-conf/)。本仓库的真实环境绑定与切换结果另见 [Web 验收记录](web-management-validation.md)。
