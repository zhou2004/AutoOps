## 实现范围

数据库管理包含数据源管理、集群管理、存储管理、备份恢复、参数配置、操作审计六个子菜单。原数据源 ID、业务分组、账号、工作台和 MySQL 终端行内虚影补全保留；数据源页没有嵌入部署或高可用面板。

- 独立建模集群、实例成员、访问入口、存储快照、仓库、备份策略/备份集、任务/步骤、配置版本和事件。同一主机的 Redis 多实例按地址、端口、服务和目录区分。
- 列表按名称、业务分组（含子分组）、引擎、环境、状态过滤。集群列表包含最近备份、当前任务；详情提供真实拓扑、五维健康、节点、复制与入口；存储、备份、参数和审计由行操作进入独立模块。
- 支持从种子只读发现及接管；接管为观察模式，调整管理级别需单独预检，不自动覆盖已有复制关系、密码或控制器。已登记控制器不重复安装。
- 新建使用 CMDB 主机、Ansible 和 systemd。受管服务带实例归属标记，不接管不明目录；保留运维工具原有安装入口与历史部署兼容数据。
- 支持 MySQL GTID/Orchestrator、PostgreSQL Patroni/etcd、Redis Sentinel、Redis Cluster 三主六从及单机。当前运维兼容范围为 MySQL 8.0、PostgreSQL 15、Redis 7.0；未知版本保留观察并显示原因。CLONE 固定安装配置要求 MySQL 8.0.24；物理备份工具配置仅开放 8.0.24–26。
- SQL 集群连接使用明确登记的写/读入口；Redis 使用 Sentinel/Cluster 原生客户端，Cluster 限 DB 0、处理 MOVED/ASK，按主分片扫描并使用带拓扑版本的复合游标。结果不明的写请求不自动重放。
- MySQL 使用独立 SSH 隔离执行器，Orchestrator 恢复前钩子直接调用，不依赖 AutoOps API。执行器核对所有已登记数据实例，对可访问实例持久设置只读保护，否则停止明确归属的服务并保留启动保护；任何独立通道无法确认隔离即返回失败。新增/退役实例同步更新隔离清单，私钥不在重复配置时轮换。
- MySQL 提供计划切换、旧主 GTID 核验和重加入、分叉修复/重建、CLONE 新副本、维护、恢复事件确认及半同步配置。显示半同步启用与实际状态，超时退化为异步不视为零丢失保证。
- PostgreSQL 默认严格同步、一个同步副本；HAProxy 使用 Patroni 角色健康检查。支持副本扩展、重建、原生滚动重启、维护、计划切换。离线旧主重建先验证已停止和目录归属，将原目录重命名为隔离目录再克隆。
- Redis Sentinel 管理复制组、quorum 和原生切换。Cluster 支持新增节点、分片/槽位迁移、迁移中断核验续行、迁空后退役及副本归属调整；增加主节点故障域分布检查和显式原生重分布操作。默认 noeviction 和至少一个有效副本写入门限。
- 存储区分实例逻辑量、物理副本占用、主机文件系统及备份存储；文件系统按主机/设备去重。业务分组阈值支持祖先覆盖，默认 80%/90%；容量预测要求至少 12 个样本且跨度至少一小时。Redis 持久化操作检查空间、内存及复制。
- 备份支持逻辑备份、固定兼容 XtraBackup 全量/增量与 binlog 时间点恢复、pgBackRest 全量/差异/增量及 WAL 恢复、Redis 按实例/分片 RDB。仓库支持本地受管目录和 S3 协议；本地完成、远端完成和恢复验证独立记录。
- 恢复使用全新目录、独立回环端口，核验后停止实例。清理保护保留窗口、增量依赖链和最后一份已验证副本；binlog 清理检查副本依赖和独立归档证据；没有直接删除 PostgreSQL WAL 的入口。
- 参数使用受控模板与原生管理器，记录实际/期望差异、版本和待重启项。已关联集群的 MySQL 工作台运行参数进入同一任务队列，绑定实际成员，保留“仅运行时”语义与单实例配置版本；未关联集群的数据源继续使用原入口和审计。
- 监控复用已有告警规则引擎；只有显式启用的规则进入原通知流程。标签为 `db_cluster_id`、`instance_id`、`engine`、`role` 等，不改变已有 `cluster` 标签。支持健康、采集过期、配置漂移、容量、持久化失败、Redis 分布风险、半同步退化等指标。已移除独立诊断页面及 API；Redis 工作台仍不使用 KEYS/长期 MONITOR。

## 任务、权限与运行方式

新 API 前缀 `/api/v1/database`，包括集群/发现/成员/能力、预检计划、任务、事件、存储、仓库、备份策略/备份、配置版本。恢复由 `restore`/`verify-backup` 操作提交，统一返回任务 ID。

计划带拓扑版本和有效期，提交使用幂等键并再次核验权限。集群变更互斥，查询与业务 DML 不进入队列。任务持久化；Worker 心跳失效后变为“结果待核验”并保留锁。接手先推进远端世代、取得远端排他锁、检查旧进程和实际状态；不能将租约过期等同于远端命令停止，不能盲目重放切换或迁槽。旧 Worker 不能覆盖接手后的任务状态或释放新锁。

新增资产类型 `database_cluster`，权限为 `db_cluster_view/manage/switch/backup/restore/config/audit`。数据源查询权限不会获得集群维护权限；新增主机须校验部署权限；提交者/API Key 的授权在执行及调度时再次核验。旧 `/cmdb/databases/*`、部署记录、备份历史仍可查询。

API 按原方式启动，数据库 Worker 独立启动：

```sh
cd api
go build -o devops .
DATABASE_PLATFORM_ROOT="$PWD/automation/database-platform" \
DATABASE_ANSIBLE_PLAYBOOK=/path/to/ansible-playbook \
./devops -mode database-worker -c config.yaml
```

验证使用私有 Ansible 2.17.14；系统原有 2.10 未替换。API 与 Worker 必须使用相同的 AutoOps 元数据库和配置，该元数据库与受管故障演练集群分离。Worker 每 30 秒采集/调度，数据状态超过 90 秒显示未知，不沿用绿色状态。Docker API 镜像、Compose 和 Kubernetes Worker 清单已更新；Kubernetes 清单仅部署 AutoOps Worker，受管数据库仍为 CMDB 主机部署。镜像构建和实际容器编排发布尚未在本次联调中执行。

PostgreSQL 控制组件固定 Patroni **4.1.5**，安装到 `/opt/autoops/patroni-4.1.5`，wheel/附属包校验 SHA256；不替换系统 Python，不升级 PostgreSQL 15.19。控制组件更新作为独立任务逐副本更新、计划切换、更新旧主。未验证的旧 Patroni 版本不能通过平台执行切换。

## 验收证据

以下 RTO 从客户端最后一次成功到恢复连续成功计算，不是管理器提升耗时。每个数字对应一次真实故障；测试负载有限，不代表生产保证。失败请求包含连接失败，不能全部解释为已送达但结果未知的事务。

| 拓扑/故障 | 三轮 RTO（秒） | 三轮确认写入数 | 确认写入丢失 |
| --- | --- | --- | --- |
| MySQL 主进程，半同步启用 | 16.102 / 17.409 / 16.035 | 25 / 31 / 19 | 0 / 0 / 0 |
| PostgreSQL 主进程，Patroni 4.1.5 | 7.174 / 7.233 / 5.461 | 28 / 27 / 24 | 0 / 0 / 0 |
| Redis Sentinel 主进程 | 8.100 / 8.195 / 7.793 | 29 / 26 / 24 | 0 / 0 / 0 |
| Redis Cluster 同一主机的三个专用进程 | 11.166 / 11.384 / 10.756 | 21 / 15 / 14 | 0 / 0 / 0 |

Redis Cluster 的主机域故障每轮前显式重新分布主节点，并核验每个复制组的跨主机副本。原生切换后主节点可能集中到同一主机，原生副本迁移也可能改变副本分布；页面和监控会报告风险，不能仅凭“三主六从”节点数宣称能承受任意后续主机故障。

### 失败、修复与不能隐藏的结果

**旧 Patroni 3.0.2 分区测试出现一条已确认测试写入丢失。** 网络恢复后出现相同 timeline 的分叉；原先短暂健康的检查不足以证明恢复成功。虽确认过两个节点可读到该记录并尝试保留分支，重启后记录仍不在当前三份数据中，因此记录为失败，未补写掩盖。旧主原目录保留在隔离目录；事件类型 `integration-data-loss` 已保存证据。固定版 4.1.5 的新分区测试、连续三轮主进程故障、严格同步和 PITR 已重新通过，但不能把旧测试改记为通过。

上游包含 etcd3 缓存一致性修复，和本次旧版现象相关；仅根据这些现象不能证明唯一根因。参考 [Patroni PR #3373](https://github.com/patroni/patroni/pull/3373)、[Patroni 发布记录](https://patroni.readthedocs.io/en/latest/releases.html)。私有启动入口还修正了 Python multiprocessing 的 main guard，避免子进程重复启动控制器。

Patroni 更新后，物理恢复发现备份中的 `hba_file` 仍引用源实例目录；任务 #189 正确保留为待核验，未标恢复成功。修复恢复配置将数据、认证、PID 和归档钩子限制到隔离环境；核验 #190 确认失败实例停止，随后 #192/#194 完成实际恢复。etcd 超过有符号 64 位范围的 Leader ID 曾被错误判为不可达，现改为无符号整数解析并添加回归测试。最后核验还复现了 etcd 健康检查后复用 HTTP 连接偶发 EOF，导致控制状态误报降级；etcd 采集改用独立连接，不重放请求，连接关闭回归测试和三节点连续五轮真实采集通过。

## 仍需外部验收与明确限制

- VIP/已有负载均衡没有资源，未验证 VIP 漂移、ARP、客户端只配置单一稳定地址的完整故障路径。
- S3 只有实现，未连接真实仓库验证认证、对象版本、容量和不可用故障；本地独立主机副本的通过不代表 S3 通过。
- 没有验证硬件 watchdog、宿主机断电、整机重启或全部网络分区组合；本次网络故障只针对专用端口，保留 SSH 等独立管理通道。所有集群的“高可用已验收”仍未置位。
- MySQL binlog 为计划任务导出已关闭日志段，不是常驻实时日志流；可恢复范围以已取得并校验的完整归档链为准。
- Redis 异步复制仍可能丢失已确认写入；逐分片备份没有跨分片统一事务快照。MySQL 半同步超时可退化为异步。测试中某几轮零丢失不能推导出 RPO=0。
- 恢复自动核验启动、文件、数据库对象/可读性；记录中注明的业务行/键值和 PITR 边界由专项联调另行验证。生产业务一致性还需业务方定义检查项。
- 安全状态机、并发幂等、过期计划、API Key 撤销、旧 Worker 世代、跨分组权限由自动化测试覆盖；不声称已经完成生产 API/Worker 容器强杀、存储系统故障和长期压力测试矩阵。
- 原生告警规则接入和匹配测试通过，本次未主动启用真实对外通知或发送消息。
- 不执行磁盘/LVM 自动扩容、直接删除 WAL、数据库大版本升级，也不部署第二套选主机制。

## 复现与测试入口

普通测试不会执行真实主机故障：

```sh
go -C api test ./...
cd web && pnpm build
```

真实测试需显式选择上述已授权隔离拓扑，例如：

```sh
DATABASE_ANSIBLE_PLAYBOOK=/path/to/ansible-playbook \
AUTOOPS_DB_LIVE_TOPOLOGY=postgresql-patroni AUTOOPS_DB_LIVE_DISCOVERY=1 \
```
